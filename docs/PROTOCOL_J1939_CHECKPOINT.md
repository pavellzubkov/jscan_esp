# Чекпоинт: доработка протокола под J1939-стриминг

> **ВНИМАНИЕ:** Этот документ **НЕ относится к текущему репозиторию TEMP_PID**.
> Он описывает доработку протокола (см. `PROTOCOL.md`) для **другого проекта**:
> ESP слушает CAN-шину J1939 и раз в 200–500 мс пушит на фронтенд массив
> самодокументируемых записей `{SA, PGN, сырые данные, период}`.
> Архитектура TEMP_PID (фрейм+CRC, WS binary, per-field PUSH) планируется к
> переиспользованию как основа. **Код в текущем репозитории НЕ меняется.**

## 1. Согласованные решения

- ESP слушает J1939-шину и динамически накапливает записи `{SA, PGN, value, periodMs}`.
- Раз в 200–500 мс шлёт массив таких записей на фронтенд (WS binary, broadcast).
- `value` = **сырые байты**: single-frame — 8 байт; multipacket — реасемблированные до 1785 байт.
- **SPN-декодирование и маппинг PGN→SPN делает фронтенд** по своей J1939-базе.
- **TP (multipacket) — обрабатывать** (`TP.CM` BAM/ACK + `TP.DT` → до 1785 байт).
- **Фрейм — переиспользовать** текущий (magic/ver/flags/len/seq/CRC), поле `UID` трактуется как `MsgType`.

## 2. Почему нужна доработка (ограничения текущего протокола)

- per-field реестр (`DataFields.inc` + `UID = fnv1a32(name) & 0xFFFF`) **не подходит**:
  набор PGN динамический и заранее неизвестен — нет имён для хэша.
- Один пакет = одно поле; **нет массива/блоб-типа** для пачки записей.
- `rx_buf_` фиксирован под max-поле (`CommModule.cpp:209`). В новом проекте ESP —
  **только отправитель**, поэтому rx-ограничение не критично; TX-буфер под батч — на куче.

## 3. Фрейм (переиспользуем; UID → MsgType)

```
Offset  Size  Поле
0       2     Magic       0x5A 0xA5
2       1     Version     = 1
3       1     Flags       бит SNAPSHOT = 0x20
4       2     MsgType     0x0001 (J1939_SNAPSHOT)   // было «UID»
6       2     PayloadLen
8       2     Seq
10      n     Batch payload
10+n    2     CRC16       (покрывает [0 .. 10+n-1], та же crc16 CCITT-FALSE)
```

## 4. Batch payload (самодокументируемые записи)

```
uint8  count
repeat count:
  uint8   sa            // source address (8 бит, из CAN ID)
  uint32  pgn           // LE, 24 бита (0..0x3FFFF)
  uint8   len           // длина data (1..1785)
  uint8   data[len]     // сырые байты PGN
  uint16  periodMs      // наблюдаемый период обновления
```

## 5. ESP-side (новый проект)

- CAN: драйвер TWAI, приём фреймов.
- J1939-декод из 29-бит CAN ID: `priority/DP/PF/PS → PGN`; `SA` (source address).
- TP-реасемблер: `TP.CM` (BAM/ACK) + `TP.DT` → сборка payload до 1785 байт.
- Снапшот-аккумулятор: карта `(SA,PGN) → {data, lastTs}`; FreeRTOS-задача читает
  очередь новых сообщений, обновляет карту и считает `periodMs` (разница таймстампов).
- Отправитель: раз в 200–500 мс сериализует карту в батч и шлёт WS (broadcast).
  Буфер на куче, размер от `count`; возможен дедуп — слать активные PGN,
  у которых истёк период.

## 6. Frontend-side (новый проект)

- TS: валидация фрейма (magic/ver/CRC) → парсинг записей (sa, pgn, len, data, periodMs).
- Декод SPN из `data` по J1939-базе (битовые смещения, resolution/offset/units).
- Динамическая таблица PGN — появляются по мере обнаружения на шине.

## 7. Что переиспользуется из TEMP_PID (идеи/архитектура)

- Фрейм + CRC16 (CCITT-FALSE, покрытие `[0..end-2]`).
- WS binary, адресная отправка по `sockfd`, per-field PUSH на connect.
- Снапшот-аккумулятор (аналог `SnapshotAggregator`).
- Логирование / дебаунс-паттерны.
