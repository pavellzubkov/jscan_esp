# Протокол связи ESP32 J1939 Scanner — версия 1

Единая спецификация бинарного протокола между прошивкой (ESP-IDF, C++17)
и веб-клиентом (TS/Vue3, WebSocket). Источник истины для обеих сторон.
Базируется на `docs/PROTOCOL_J1939_CHECKPOINT.md` (доработка протокола TEMP_PID
под J1939-стриминг).

Версия протокола: **1** (поле `version` в заголовке).
Передаётся как WS **binary**-фрейм (`HTTPD_WS_TYPE_BINARY`).

> Пока на ESP используется **старый** фронт из `spiffs_image/` (не понимает
> этот протокол). Новый фронт пересобирается отдельно под эту спецификацию.

## 1. Формат пакета (заголовок)

```
Offset  Size  Поле
0       2     Magic       0x5A 0xA5  (фиксированная сигнатура)
2       1     Version     = 1
3       1     Flags       битовые флаги
4       2     MsgType     uint16 LE (см. §5)
6       2     PayloadLen  uint16 LE, длина payload
8       2     Seq         uint16 LE, монотонный счётчик отправителя
10      n     Payload     данные (см. §4)
10+n    2     CRC16       uint16 LE
```

`totalLen = 10 + PayloadLen + 2`.

### Flags (байт 3)

| Бит | Значение | Имя | Смысл |
|-----|----------|-----|-------|
| 5 | 0x20 | SNAPSHOT | пакет — батч снапшота J1939 |

Остальные биты зарезервированы (0).

### CRC16
- Алгоритм: CRC-16/CCITT-FALSE, полином `0x1021`, init `0xFFFF` (табличная
  форма, как в `J1939Proto::crc16`).
- Покрытие: **байты [0 .. totalLen-3]** (весь пакет, включая magic, исключая
  2 байта CRC).
- Передаётся младшим байтом первым (little-endian).
- Справочная (TS, рефлексированная) реализация:

```ts
export function crc16(data: Uint8Array): number {
  let crc = 0xffff;
  for (let i = 0; i < data.length; i++) {
    crc ^= data[i];
    for (let b = 0; b < 8; b++) {
      crc = (crc & 1) ? ((crc >> 1) ^ 0x8408) : (crc >> 1);
    }
  }
  return crc;
}
```

Рефлексированная форма эквивалентна прямой CCITT-FALSE при том же покрытии —
проверять хэш-тестом.

## 2. MsgType

| Значение | Имя | Направление | Payload |
|---|---|---|---|
| 0x0001 | `J1939_SNAPSHOT` | ESP → клиент | батч записей (см. §3) |
| 0x0002 | `J1939_REQUEST` | клиент → ESP | `{dstAddr u8, pgn u32 LE}` (см. §4) |

---

## 3. J1939_SNAPSHOT (ESP → клиент)

### 3.1 Batch payload

```
uint8  count                       // количество записей (0..255)
repeat count:
  uint8   sa                       // source address (из CAN ID, 8 бит)
  uint32  pgn                      // LE, 24 бита (0..0x3FFFF)
  uint8   len                      // длина data (1..1785)
  uint8   data[len]                // сырые байты PGN (single-frame 8 байт;
                                   // multipacket — реасемблированный до 1785)
  uint16  periodMs                 // LE, наблюдаемый период обновления записи
```

- `value` = **сырые байты**. SPN-декодирование и маппинг PGN→SPN делает
  **фронтенд** по своей J1939-базе.
- Период публикации батча: 200–500 мс (по умолчанию 250 мс, конфиг
  `snapshotIntervalMs`).
- Отправляются **активные** записи — те, что обновлялись не дольше
  `snapshotTtlMs` (по умолчанию 2000 мс). Запись с истёкшим TTL исключается
  из батча, пока не обновится снова.
- `periodMs` = разница монотонных таймстампов между двумя последовательными
  получениями одного (SA,PGN). Для первой записи = 0.
- Клиент не запрашивает состояние: сервер сам шлёт снапшоты broadcast'ом
  всем подключённым WS-клиентам.

### 3.2 Пример (упрощённый, 2 записи)

```
[5A A5] [01] [20] [01 00] [0E 00] [00 00]          <- заголовок, payload=14
  count=02
  sa=00  pgn=00 F4 00 (65227)  len=08  data(8 байт)  periodMs=EA 00 (234)
  sa=03  pgn=01 F4 00 (65228)  len=08  data(8 байт)  periodMs=EA 00 (234)
[CRC lo][CRC hi]
```

## 4. J1939_REQUEST (клиент → ESP)

ESP получает кадр, разбирает payload, публикует внутреннее событие
`J1939_REQUEST`, `J1939System` отправляет по CAN-шине RQST (PGN 59904,
priority 6).

Payload (5 байт):
```
uint8   dstAddr   // адрес узла, которому адресован RQST (например, адрес ЭБУ)
uint32  pgn       // LE, запрашиваемый PGN (например 65227 = DTC)
```

Ответа по протоколу нет: результат (запрошенный PGN) придёт обычным пакетом
`J1939_SNAPSHOT`, когда узел начнёт передавать данные.

---

## 5. Сценарии обмена

1. **Подключение клиента**: сервер логирует, но ничего не шлёт сам по себе
   (в отличие от per-field PUSH в TEMP_PID). Состояние J1939 приходит первым
   же снапшотом.
2. **Телеметрия**: каждые `snapshotIntervalMs` сервер шлёт broadcast батч
   `J1939_SNAPSHOT` всем клиентам.
3. **Запрос PGN**: клиент шлёт `J1939_REQUEST`; ESP шлёт RQST на шину; когда
   данные придут — они попадут в следующие снапшоты.

---

## 6. Ограничения

- Максимальная длина payload батча: 8192 байт (`kMaxBatchPayload`).
  `totalLen ≤ 8202` байта (`kMaxWsMessageLen = 8192` + 10 заголовка).
- Максимум записей в аккумуляторе: 128 (`maxTrackedPgns`, конфиг).
- Максимальная длина одного PGN-данных: 1785 байт (255 пакетов TP.DT × 7).
- При переполнении батча записи, не влезшие в 8192 байта, отбрасываются на
  стороне ESP (порядок: сначала более «свежие»). Клиент должен уметь принимать
  частичные наборы.

## 7. Советы по TS/Vue клиенту

- Читать `event.data` как `ArrayBuffer`/`Blob` → `Uint8Array`/`DataView`.
- Проверять: `[0..1]=0x5A 0xA5`, `[2]==1`, CRC по `[0..len-3]`.
- `MsgType` — `[4..5]` LE: `0x0001` = снапшот, `0x0002` = запрос (только для
  исходящих от клиента).
- В снапшоте: `count = payload[0]`; итерировать записи, читая
  `sa(1) pgn(3 LE) len(1) data(len) periodMs(2 LE)`.
- Динамическая таблица PGN: записи добавляются/обновляются по `(sa,pgn)`,
  удаляются/гаснут по `periodMs`/TTL (нет TTL в кадре — клиент сам засекает
  отсутствие обновления записи дольше ~`snapshotTtlMs`).
